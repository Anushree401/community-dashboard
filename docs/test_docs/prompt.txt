# Community Engagement Hub (CEH) — Build From Scratch

Act as my senior full-stack engineer, software architect, and technical mentor. Help me build a complete, production-minded **Community Engagement Hub (CEH)** from scratch.

**Important:** This is a completely new implementation. Do not inspect, reuse, migrate, repair, or depend on any previous project or codebase. Treat this as a greenfield project with a clean directory structure, fresh dependencies, and a properly designed architecture.

## 1. Project Overview

Community Engagement Hub (CEH) is a web-based platform for managing online communities, facilitating member participation, and analyzing community engagement through dashboards and visualizations.

The platform should allow members to join communities, participate in discussions and events, receive announcements, and track their engagement. Administrators and moderators should have tools to manage communities, members, content, and activities.

The objective is to build a functional, secure, polished application rather than just a UI prototype.

## 2. User Roles

### Community Member
- Register, log in, and manage their profile.
- Discover and search communities.
- Join public communities and request access to private communities.
- Create posts and comments.
- Participate in community discussions and activities.
- View and RSVP to events.
- Read announcements.
- Track engagement points, badges, and leaderboard rankings.

### Community Administrator
- Create, edit, and manage communities.
- Approve or reject membership requests.
- Add, remove, and manage community members.
- Assign roles and permissions.
- Publish announcements.
- Create and manage events.
- Moderate community content.
- View community analytics and engagement reports.

### Moderator
- Moderate posts, comments, and member activity according to assigned permissions.
- Assist with community management.
- Access only the administrative actions explicitly granted to them.

A community creator should automatically become that community's administrator.

## 3. Core Features

### A. Authentication and user management
- Registration and login.
- Secure authentication and session/token handling.
- Protected pages and API endpoints.
- User profiles and profile editing.
- Appropriate handling of unauthorized and expired sessions.

### B. Community management
- Community creation and discovery.
- Search, categories, and tags.
- Public and private communities.
- Membership and join-request workflows.
- Member lists and membership status.
- Community-specific role-based access control.

### C. Discussions and interactions
- Create, edit, and delete posts according to permissions.
- Comment on posts.
- Record likes or other supported interactions.
- Enforce ownership and community-access rules.
- Track interactions for analytics.

### D. Events
- Create, edit, and manage community events.
- Display event dates, descriptions, and details.
- RSVP and track participation.
- Restrict event-management actions to authorized users.

### E. Announcements
- Publish and manage community announcements.
- Display announcements to eligible members.
- Maintain appropriate permissions for publishing and editing.

### F. Analytics dashboard
Build dashboards that display real application data, including:
- Total members.
- Active members.
- New-member growth.
- Posts, comments, and interactions.
- Engagement trends over time.
- Popular discussion topics.
- Member retention.
- Engagement heatmaps.
- Community activity summaries.
- Leaderboards and participation statistics.

Use charts and visualizations where they improve understanding. Clearly distinguish unavailable metrics from actual zero values. Do not fabricate analytics data.

### G. Gamification
- Engagement points.
- Badges and achievement milestones.
- Leaderboards.
- Transparent rules for earning points.
- Protection against duplicate or manipulated point awards.

### H. Realtime updates
Where appropriate, support live or near-realtime updates for announcements, community activity, and relevant dashboard information. Choose an implementation that fits the selected backend and database.

## 5. Security Requirements

Security must be designed into the application from the beginning.

Implement:
- Server-side authentication verification.
- Role-based access control.
- Least-privilege authorization.
- Input validation and sanitization where appropriate.
- Resource ownership checks.
- Protection against privilege escalation and insecure direct object references.
- Secure configuration and secret management.
- Appropriate CORS policies.
- Rate limiting and abuse prevention where needed.
- Consistent error handling.
- Logging without exposing credentials, tokens, or sensitive user information.
- Database access rules appropriate to the application's trust boundaries.

Never trust user IDs, administrator flags, role assignments, or permissions supplied by the client. Use verified identity information and trusted server-side authorization data.

Test both allowed and denied access paths. Do not claim security has been verified without running the relevant tests.

## 6. Data Model

Design a consistent Firestore data model before implementing the main features.

Consider entities or collections for:
- Users.
- Communities.
- Community memberships.
- Role definitions and permissions.
- Posts.
- Comments.
- Events.
- Event RSVPs.
- Announcements.
- Notifications, if implemented.
- Engagement activities.
- Points and badges.

For each collection, define:
- Document identifiers.
- Required and optional fields.
- Relationships between records.
- Access-control rules.
- Query patterns and indexes.
- Data-integrity constraints.
- Strategies for pagination and scalable reads.

Avoid unnecessary duplication of membership and permission data. Consider Firestore's querying limitations, document-size limits, and read/write costs when designing the schema.
